# 历史银行重复记录审核：本次发布边界

本次采用安全禁用方案发布 PR #18：保留审核、只读导出、自动照合、现金、立替及法人卡功能；历史银行重复记录取消/恢复不作为可用功能发布。

## 强制边界

- UI 所有取消/恢复按钮均禁用，直接调用处理器也拒绝，不入同步队列。
- 业务服务在读取记录或开启事务之前无条件拒绝 `bankCancelDuplicate` / `bankRestoreDuplicate`，包括 demo 项目。不能通过伪造 projectId 打开。
- Firestore Rules 对所有经客户端提交的银行明细写入强制执行：不能创建/写入 `cancelled`、`duplicateCancellation` 或非空 `deletedAt`；既有这类历史记录也不能更新或恢复；银行物理删除继续拒绝。
- 因此取消与新反向引用竞态中，取消永远不能提交。不存在用浏览器先扫描集合证明“没有引用”的假设。本次不声称实现可启用的反向引用锁。
- 受信任 Admin SDK 不受 Rules 限制；本次不新增、运行或部署任何 Admin SDK 历史修改入口。
- 纯领域层旧取消算法仅保留为不可达的测试/草稿代码。未来启用必须另行实现受信任事务查询或 Rules 强制引用锁，并完成并发验证，不能简单删除 gate。

## 验证

- 172 项 Node 单元测试及静态/PWA 检查通过。
- 40 项真实 Firestore Rules/集成测试通过，新增直接绕过业务入口的伪造取消、软删除、创建取消记录、历史恢复/修改、并发新增引用与失败事务无残留检查。
- `payment-paths-browser.cjs` 增加 390px / 1280px 真实模拟器审核 UI 与业务服务拒绝测试；保留四条付款路径的原始回归。
- `scripts/test-browser-suite.cjs` 分组串行执行全部本地与模拟器浏览器回归；CI 安装 Node 22、Java 21、Playwright Chromium 并运行完整发布检查。

## 数据与部署

本次只提交应用和安全规则，不读取或修改正式 Firestore 历史账目、不做生产迁移、不再次删除此前「メイン口座」31条记录。Rules 部署只改变访问策略，不改变数据。应用 JSON 导出仍不等于原生 Firestore 恢复备份，也不是单事务快照。
