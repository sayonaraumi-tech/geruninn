# Lifecycle audit before changes

Baseline: main b49e944; clean independent clone. No production data read or mutated.

- Calendar creation exists with deterministic Google IDs and 409 recovery, but imports only propagate workDate. Location/notes are not mapped. Month-range import misses linked events moved to another month. Background work only exports, not imports. Acknowledgements can clear a newer revision after a slow request. Event lookup uses Google event ID without calendar identity.
- Standalone receipt deliberately creates no sales/payment/cash ledger (39b9df3 and standalone-receipt tests). This conflicts with requested cash accounting. Explicit linked receipts create payments only; keep that behavior to avoid duplicate sales. Staff rules only permit invoice/onoda sales and require payment target to exist before transaction, so atomic receipt + sale needs matching rules.
- Latest source has working admin-only saved-document actions, no disabled void button. Earlier UI symptom cannot be reproduced from source alone. Direct void is blocked for any linked payment, even unconfirmed payments. Formal documents are immutable; reasons and audit logs required. Do not bypass admin claims or delete actual confirmed payments. Improve pending-payment invalidation and surface permission/restriction feedback.
- Voided sales are excluded by live(), but monthly income independently counts payments and can include payments associated with invalid sales. Exclude known invalid anchors.
- acceptEstimate preserves old date on blank input and uses raw, unnormalized date in schedule. Revision supplied by UI is ignored. No explicit project schedule/address/notes editor exists.
- Payroll/attendance are absent from this repo; do not touch any separate modules or production rules outside this checkout. companyId remains tsukinowa. No backfill or data deletion.

Plan: audited atomic lifecycle commands; deterministic receipt-owned accounting; permitted date/location/notes synchronization, conflict/replay protection and linked-event reads; browser/domain/rules regression tests. Preview only; no production deployment.

## Implemented and verified

- Construction schedule edits have an explicit UI entry for date/location/notes. Import writes permitted fields to estimate/project records, preserves official snapshots and money, handles cross-month moves through linked-event polling, and retains Google deletion tombstones. Calendar identity includes calendar ID; unchanged imports enqueue no command. Export preserves remote notes unless a local note edit is pending. Acknowledgements compare the sent schedule fields and cannot clear a newer edit.
- Pending payments can be soft-cancelled in the same audited invoice invalidation transaction. Confirmed cash/bank payments remain protected until their actual cancellation/refund relationship is resolved. Staff see an explicit permission explanation. No direct claim escalation, physical deletion or Firestore bypass.
- Cash receipts create a deterministic sale, payment and cash ledger row atomically. Linked invoice receipts reuse sales. A subsequent invoice for the same calendar event adopts the receipt sale; later receipt revisions do not steal invoice ownership. Rules permit this atomic staff workflow and require the formal document to be part of the same operation.
- Old independent cash receipts have an admin-only, reason-required reconciliation action. It can explicitly attach to an existing sale or create an independent sale; it preserves the original receipt snapshot and is idempotent. No automatic name/amount guessing and no production backfill performed.
- Invalid invoice anchors are excluded from sales, receivables and income projections, including inconsistent legacy records. Original payment/cash records remain available for audit.

Production account claims, deployed bundle and deployed Firestore rules were not inspected; do not claim the user's precise production cause is confirmed.

The repo has no dedicated payroll/attendance implementation. Those modules were not changed or verified. Production rules must be compared/merged with the live project's rules before deployment, particularly if separate modules share that project.

Google synchronization runs while the app is open, online, cloud-authenticated and Calendar OAuth is valid. Tokens are client-side and expire; no silent persistent server-side refresh token or closed-browser worker was introduced. A 15-second interval checks linked events, not every unrelated calendar event. Pending local scheduling changes take precedence until exported; remote changes then import. Remote financial/title changes do not edit formal accounting. Google deletion is recorded, not treated as invoice cancellation or refund.
